# Build speed — что измерено, что решено, что осталось

Документ существует потому, что решения по скорости сборки принимались трижды
и каждый раз забывались. Здесь только замеры и выводы; менять цифры можно
только новым прогоном, а не оценкой.

## Базовая линия (run 37046212026, v3.9.30)

| Этап | Время |
|---|---|
| Release guard | 26 s |
| Build for testing | 248 s |
| Test (1 воркер) | **689 s** |
| Build for device | 368 s (параллельно с тестом) |
| Упаковка + публикация | 57 s |
| **Итого** | **≈23 мин** |

## Решено и проверено

1. **Тесты и сборка под устройство идут параллельно** (было последовательно).
   Выигрыш: ~368 s, цена нулевая — публикация всё равно ждёт оба.
2. **SPM-кэш включён.** Полный кэш DerivedData — выключен: восстанавливался за
   15 s и не ускорял, зато давал шанс собрать против устаревшего бандла.
3. **`test-without-building`** — тесты не пересобираются вторым проходом.
4. **`-parallel-testing-enabled NO`, 1 воркер.** Отвергнуто замером: 4 воркера =
   **4016 s** против 689 s (run 37123440609). Четыре клона симулятора дерутся за
   ядра одного раннера и каждый заново ставит приложение. Параллелизм, который
   действительно работает, — между *job'ами*, а не внутри сьюта.

## Внедрено 24.10.2026: три шарда

`scripts/test_shards.py` находит все `XCTestCase` в `HermesMobileTests/` и
раскладывает их по трём корзинам **по числу тест-методов** (жадно, по убыванию
нагрузки, при стабильном порядке имён).

Текущая раскладка: **627 / 639 / 634 кейса** (143 класса, 1900 тестовых методов).

Почему не список классов руками: список тихо перестаёт покрывать новые тесты —
шард, куда они должны были попасть, зеленеет, а тесты не запускаются вообще.
Скрипт перечитывает исходники на каждом прогоне.

Почему три отдельных job'а, а не один job с тремя воркерами: см. пункт 4 выше.
Каждый шард собирает тесты сам (248 s), зато идёт параллельно остальным.

**Ожидаемый эффект:** тест-этап из 689 s превращается в ~230 s, общий прогон с
~23 мин до ~15–17 мин. Ожидание подтверждается или опровергается замером
первого же прогона — цифры вписываются сюда после него.

## Что осталось и почему не сделано

- **Шаринг сборки между шардами** (артефакт DerivedData): экономит 2×248 s, но
  скачивание сопоставимо по времени и появляется риск собрать против устаревшего
  бандла. Отклонено, пока шарды не покажут себя.
- **Не гонять полный сьют на каждой ветке**: экономит ~10 мин на попытку, но
  ослабляет гейт — красный тест сможет дойти до main. Требует отдельного решения
  владельца.
- **macOS-раннер: очередь.** Аннотация GitHub: «jobs targeting macOS arm64
  runners may experience longer queue times». Это не наш код; видно как разрыв
  между `created_at` и `run_started_at`.

## Правило

Любое изменение этого файла сопровождается ссылкой на прогон, которым оно
измерено. «Должно стать быстрее» — не результат.
